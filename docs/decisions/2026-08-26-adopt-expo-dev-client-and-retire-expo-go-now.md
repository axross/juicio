# Adopt expo-dev-client and Retire Expo Go Now

`2026-08-26-adopt-react-native-legal-and-drop-expo-go.md` already establishes
that Expo Go leaves this project: `react-native-legal` is a native module and
its own README states it cannot run under Expo Go, so adopting it removes
Expo Go from the development flow. That record's reasoning still holds and
this one does not supersede it — only the timing moves. `react-native-legal`
itself, and the `Licenses` row it backs, are out of scope for this change; a
follow-up issue owns them.

`expo-dev-client` is adopted **here**, in this change, rather than waiting
for that follow-up. Because this is a Continuous Native Generation project
(`/android` and `/ios` are gitignored, regenerated by `expo prebuild`),
adopting it is a dependency addition and nothing else: no `plugins` entry in
`app.json`, no committed native change, and the next `expo prebuild` — which
`expo run:android` performs on its own — links the module. `npm run dev`
needs no new flag: with `expo-dev-client` installed, `expo start` targets a
development build automatically, and the `--dev-client` flag exists only for
projects that lack the package. Every path this repository documents that
named Expo Go — the README's prerequisites bullet and its numbered steps —
is rewritten to describe the development-build flow instead.

The cost is real and is recorded here rather than left to be discovered: a
native toolchain is now required to run the app at all, where before Expo Go
let a contributor scan a QR code and skip it. Building for iOS additionally
needs Xcode, and therefore macOS — `expo run:ios` has no other path. This
change does not soften that cost; it is the real price of retiring Expo Go
now rather than later.

Two alternatives were rejected, both weighed at the plan gate.

**Declaring Expo Go unsupported in documentation only, without adopting
`expo-dev-client`.** Rejected because it would make the README describe a
policy rather than a fact: Expo Go would keep working right up until the
change that actually breaks it, and a contributor reading "Expo Go is
unsupported" while it still launches the app has no reason to believe it.

**Leaving Expo Go in place until `react-native-legal` lands.** Rejected
because it puts a dependency addition, a native-module compatibility risk, a
new screen, and a repository-wide change to how everyone works into one
review — exactly the bundling `2026-08-26-adopt-react-native-legal-and-drop-expo-go.md`'s
own split was meant to avoid. Retiring Expo Go now, ahead of that dependency,
lets this change be reviewed on its own, and means the development build
`react-native-legal` will need is already the normal way to work here by the
time it arrives.

**Setting up EAS Build so an iOS development build could be produced without
a Mac.** Considered, because it is the only documented answer to the macOS
requirement this change introduces, and deliberately not adopted here. It
needs an Expo account, an Apple Developer Program membership for device
distribution, and a build configuration this repository does not have — a
decision of its own, not a detail of this one. This project's existing
deviation from `expo-app-development`'s EAS-flavoured defaults, recorded in
`docs/operations/agent-skills.md`, is unaffected: this project still does
not use EAS Build, Submit, Update, or Workflows.
